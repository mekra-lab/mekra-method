# OKF v0.2 → v0.3

This document summarizes only the changes in the official v0.3 specification that affect existing bundles and Mekra operations. The canonical source for detailed rules is [official SPEC §13](https://github.com/open-knowledge-format/open-knowledge-format/blob/527e81aff55992be21507e97004286789126f88c/SPEC.md#13-changes-from-v02). The official repository has moved to [open-knowledge-format/open-knowledge-format](https://github.com/open-knowledge-format/open-knowledge-format).

Existing v0.2 bundles remain valid. Most of v0.3 clarifies the rules in v0.2. Only the two changes below affect how existing values are read. If migrating is worthwhile, work through the checks in order and change `okf_version` last.

## Two changes in how values are read

| Change | Impact on existing bundles | What to check |
| --- | --- | --- |
| Path field values that do not start with `/` resolve from the directory of the file containing them. | Relative paths in fields such as `resource`, `sources[].resource`, and `computation` may point to a different target or break in files in subdirectories if they were written relative to the bundle root, as in the v0.2 examples. Consumers can try resolving from the root as a fallback for bundles that declare v0.2 or earlier or omit the version. Declaring `"0.3"` removes that fallback. | Find path field values in concepts in subdirectories and resolve each from both the file's directory and the bundle root. If the root-relative target is the intended one, prefix the value with `/`. If both locations contain a file with the same name, compare the actual targets, since the target can change without breaking the link. Markdown body links were already resolved relative to the file in v0.2. |
| The trust tier uses only verification at or after `generated.at`. | A concept whose content changed without subsequent verification may drop from human-reviewed to a lower tier. | A lower tier is the safer outcome. Leave verification timestamps and records alone unless you actually verify the content again. Select only the concepts that need rechecking and verify them. |

## Clarified rules

- **Identifying concepts.** The names `index.md` and `log.md` are reserved at every depth. Other `.md` files count as concepts only if their frontmatter contains a non-empty `type`. Files such as `README.md` and `AGENTS.md` can still belong to a conforming bundle without `type`, in which case they do not count as concepts. Files without the `.md` extension are assets. Files and directories whose names start with `.` are excluded from the bundle.
- **Paths outside the bundle.** Links and paths that resolve outside the bundle root are external references. Strict consumers do not read their targets from the local filesystem. Agents reading the full repository can use them as discovery paths. The targets are unavailable when the bundle is used on its own.
- **Frontmatter.** Follow the YAML 1.2 core schema and use each key only once. Quote string values that look like numbers or booleans (`okf_version: "0.3"`).
- **Timestamps.** Use a date-time with an offset or a date alone. A date alone represents midnight UTC at the start of that day. A date-time without an offset is invalid.
- **Lifecycle.** An omitted `status` defaults to `stable`. Values outside the list (`draft`, `stable`, `deprecated`) do not count as `stable`, so consumers that filter for current knowledge exclude concepts with those values. `stale_after` means “time to recheck.” An unreadable value does not count as fresh.
- **Relationships.** Links express directed, untyped relationships. Typed relationships are outside the v0.3 standard.

## Optional features to adopt

- **`superseded_by`.** Use it with `status: deprecated` to point to the replacement concept's path. When moving or renaming a concept, leave a short deprecated concept at the old path to keep existing references working. Use links in the body for ordinary related documents.
- **Bundle metadata.** The bundle-root `index.md` may include `title`, `description`, `license`, and extension keys in its frontmatter. Leave frontmatter out of `index.md` files in subdirectories. Tools that regenerate the index must preserve the existing root frontmatter. Fill in metadata only when there is a bundle name and scope to convey. Omit `license` if you have no basis for it, instead of leaving it blank.
- **Extension keys.** Preserve unknown keys at every level. Future versions of the official specification will leave keys beginning with `x-` available for extensions. If you need Mekra-specific information, you can use a prefix such as `x-mekra-`. Wait until there is an actual use for an extension key before adding it.

## Checking the tools you use

Some tools have yet to support v0.3. As of 2026-11-23, Google Knowledge Catalog's `kcmd` supports OKF as documented for v0.2 and rejects a push if `bundle/` contains a `.md` file without `type`. If you need to exchange bundles with tools like this, you can keep `okf_version: "0.2"` and include `type` in every Markdown file. Check which version your tools support when you use them.

## The Mekra templates and this guide

Mekra's [template bundle](../../templates/mekra/index.md) and this guide's [operating knowledge](../../okf/index.md) declare v0.3. Both bundles use only URLs in path fields and omit trust fields, so link resolution and trust tiers are the same as in v0.2. In bundles that Mekra puts together, treat documents with frontmatter as concepts and always give them a `type`. This authoring convention keeps intended concepts from being skipped when `type` is missing. The convention goes beyond the specification's requirements. See [the role and use of OKF](../../okf/okf-format.md) for the reasoning.

## Checklist

- Do path fields in concepts in subdirectories resolve to the intended targets relative to the files that contain them?
- Have you updated verification records for changed concepts only where you actually rechecked the content?
- Are concepts with unlisted `status` values excluded from current knowledge only when you intend them to be?
- Can the tools you use read v0.3 and Markdown files without `type`?
- After making these checks, did you set `okf_version` in the bundle-root `index.md` to `"0.3"`?
